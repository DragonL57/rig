# Workflow

Use this playbook to plan, delegate, and close implementation. The main agent plans and orchestrates. It writes a change that fits one file and 30 lines itself. Every delegated change goes to an `implementer` and gets a reviewer.

Every step that applies runs. A delegated change takes the review step. Do not ask the user whether to review. A change whose review step did not run is reported as a defect in the run.

## Roles

The specialists `implementer`, `taste-reviewer`, `spec-reviewer`, `docs-reviewer`, `test-reviewer`, `uiux-reviewer`, `final-reviewer`, and `fallback-runner` are defined in the harness's agent directories. The implementer is the only editing role; reviewers inspect and report. Each specialist runs the model in its agent definition, or the session model when it names none; give `fallback-runner` an explicit model different from the writer's. On a harness without subagents, apply the roles through separate sessions or one agent adopting each role; when delegation is unavailable, name the spawn that failed, then do the work yourself against the same definition and say so. Report the missing spawn as a defect in the run. The work you do yourself is not the review step.

## Steps

1. **Write the plan.** A request with 2+ steps gets a plan before the first edit; reading, searching, and running read-only commands to write it is expected. The plan names what changes, in which files, the steps with their checks, the exit condition as a command whose success settles it (`Done when: <command>`, a read-back for a document), a default for each open decision, the sketch from `.rig/playbooks/design.md`, and what is out of scope. Where the repository has `backlog/`, reuse an open task that covers the work or create one with `backlog task create "<title>" --plain`, then record the plan with `backlog task edit <id> --plan "<steps>"` and the acceptance criteria with `--ac`. Then run `todo list` and `todo create` for the session steps, reusing an open task that covers the work and creating one only for work the list does not have. When the work splits into slices, the plan lists each slice's files and states that no shared registry, key, migration number, branch, generated artifact, or test helper crosses them, following `.rig/playbooks/parallel.md`. Use grilling when the user asks or when an unresolved product choice that belongs to the user blocks the plan.
2. **Review the plan.** Send the plan to `spec-reviewer` before any code exists, and to `taste-reviewer` when the shape is a product choice the user will see. Send it to `uiux-reviewer` when the plan describes a new screen or flow. Set the budget from `.rig/playbooks/review.md` step 3. Fix what they find, and tell the user what you rejected and why.
3. **Get the user's approval.** Build nothing before the user approves the reviewed plan. An autonomy grant satisfies the approval for the work it names.
4. **Write the invariants as failing tests** for shipping code, and watch them fail, following `.rig/playbooks/testing.md`.
5. **Hand off to the implementer** for a delegated change. The failing tests are the verified first edit that proves the approach. Give it the approved plan; a map of the relevant files and what matters in each; rejected approaches and why; the landed first edit and its verification; the remaining steps and their checks. Disjoint slices go to parallel implementers in the same checkout, following `.rig/playbooks/parallel.md`; the brief names the slice's files and the rule that its check covers only those, reporting a failure outside them instead of editing it. The parallel path runs no git command. The implementer stops and reports when the handoff contradicts the real code.
6. **Review** a delegated change once near the end of a logical slice with `.rig/playbooks/review.md`. A change is a branch against its base, a range of commits on the default branch, or the working diff. Parallel work takes one integration pass after the slices land instead of a review per slice. Report the change with one line naming each reviewer that ran and its verdict, as `Written by: implementer, 3 files. spec-reviewer: clean. taste-reviewer: changes needed.` A single edit in one file reports `spec-reviewer: not run, single-file exemption.`
7. **Verify and stop.** Read the diff, run proportionate checks, and trace the affected path when needed. Run a check, never sit through it. Do not wait out a long real period (timer, cron, timeout, retry backoff) to prove it works: copy the artifact with a short period, or read the scheduler's computed next elapse, then delete the copy. A test that would block for minutes is a test to redesign. Once current criteria and checks pass, remove dispensable work and stop.
8. **Hand off the session state** where the next session will find it: the task notes, plus the handoff this harness provides. Do this once a delegated change is verified.
9. **Commit once.** After the spec is done and reviewed, make the single commit, or a `/pistate snapshot`, on the user's go-ahead.
